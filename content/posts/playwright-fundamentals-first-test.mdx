This is Part 1 of a three-part series on getting productive with
Playwright. We'll write a real test against a real page, not a toy example,
and explain what each line is actually doing.

## Installing Playwright

```bash
pnpm create playwright
```

This scaffolds a `playwright.config.ts`, an example test, and installs the
browser binaries (Chromium, Firefox, WebKit) the test runner needs.

## Writing your first real test

Here's a test against a login form — the kind of thing you'll write
constantly in real projects:

```ts
import { test, expect } from "@playwright/test";

test("user can log in with valid credentials", async ({ page }) => {
  await page.goto("/login");

  await page.getByLabel("Email").fill("[email protected]");
  await page.getByLabel("Password").fill("correct-horse-battery-staple");
  await page.getByRole("button", { name: "Sign in" }).click();

  await expect(page.getByText("Welcome back")).toBeVisible();
});
```

A few things worth calling out:

- **`getByLabel` and `getByRole`** are Playwright's recommended locator
  strategy — they query the accessibility tree, the same way a screen
  reader or a real user would find these elements. This tends to produce
  far more stable tests than CSS selectors tied to implementation details.
- **`await expect(...).toBeVisible()`** isn't a one-shot check. Playwright
  retries this assertion automatically until it passes or times out, so you
  don't need manual `sleep()` calls to wait for the page to update.

## Running it

```bash
npx playwright test
```

Add `--ui` for Playwright's interactive UI mode, which is the fastest way
to debug a failing test — you get a full timeline, DOM snapshots at every
step, and network activity, without adding a single `console.log`.
